## Instance backup, scoped API tokens, signed images, access protection, scheduled jobs, PostgreSQL point-in-time recovery and replicas, Git over SSH, canary deployments, shared variables, Vault and Key Vault secrets, service catalogs, import from Coolify, Heroku and Dokku, observability, compliance report, configuration as code and an MCP server for AI agents

### New

- **Instance backup** (*Settings → Backup storage*): PortDock backs up its own database and the key that encrypts the secrets in it, on a schedule or on demand. Backups are encrypted with a passphrase in the standard [age](https://age-encryption.org) format, the last N are kept on the server and, optionally, in the S3 bucket (`portdock/instance/`), and a failure sends a `backup.failed` notification.
- **Restore on a new server**: the first-run page offers *Restore it from a backup*: upload the file, type the passphrase, and PortDock restarts with every account, project, setting and connection of the old instance. `portdock -restore <file>` does the same from the command line.
- **Roll back the running instance**: the owner can restore any backup from the list, or copy one from S3 to the server first. The replaced data is kept in `/data/portdock/restore/replaced-*`.
- A backup can also be opened without PortDock: `age -d` gives a `.tar.gz` with `portdock.db`, `secret.key` and `manifest.json`.
- **API tokens with a scope** (`read`, `deploy`, `write` or `full`), **limited to some projects** if needed, and **with an expiry date**. A token acts with the rights of its account, capped by these limits; a limited token is never an administrator, and no token can manage accounts or create other tokens. Existing tokens keep full access.
- **Service accounts** (*Settings → Team*): accounts for CI pipelines and scripts, with no password and no sign-in. Administrators create their tokens, they get project access like people, and their actions are logged under their own name.

- **Signed images with an SBOM.** Release images are signed by the release workflow with Sigstore keyless signing and carry an SPDX SBOM and a SLSA provenance attestation; the SBOM is attached to the GitHub release.
- **Updates check the signature.** Before installing a version, PortDock runs `cosign verify` and accepts only a signature from the release workflow of the update repository, for a version tag, then installs exactly that digest. *Settings → Updates → Image signature* can be set to *warn* for networks that cannot reach Sigstore. Versions before v1.14.0 are not signed, so this applies from the next update on.
- **Checks on every change:** each push and pull request runs the Go tests with the race detector, `govulncheck`, the TypeScript and translation checks, `npm audit` and an image build; CodeQL analyzes the code and Dependabot proposes dependency updates.

- **Access protection for applications** (Domains tab), applied by the proxy on every domain and preview, without a redeploy:
  - **Single sign-on with PortDock**: visitors sign in to PortDock (with the company's SSO or LDAP when configured) before reaching the application; choose people with access to the project or every PortDock user, optionally only some addresses or `@domain`s. The application receives `X-Forwarded-User`, `X-Forwarded-Email` and `X-Forwarded-Name`.
  - **Password** (basic authentication), **allowed addresses** (IP / CIDR, behind a CDN if needed) and a **rate limit** per visitor address.

- **Scheduled jobs** (Jobs tab of an application): commands run on a cron schedule in the instance time zone, in a new container of the application's current image with its variables and persistent storage (or inside a running service of a compose application). Each run keeps its status, exit code, duration and output; runs have a timeout, never overlap, can be started by hand, and a failure sends a `job.failed` notification.

- **Test restores of database backups**: a backup is restored into a temporary container of the database's image, then PortDock counts what it holds and removes the container. The container has no network, no port and none of the database's volumes, so the database itself is not touched.
  - Every engine is covered: PostgreSQL, MySQL, MariaDB, SQL Server, MongoDB, ClickHouse, Redis and Valkey.
  - Run it on demand (*Test restore* on a backup) or on a schedule for the latest backup of a backup schedule.
  - A failure sends `backup.verify_failed`. Prometheus exports the last result of each database.
- **Point-in-time recovery for PostgreSQL** (Backups tab): restore a database as it was at any second of the recovery window.
  - Continuous WAL archiving to the database's server, with at most one minute of changes not yet archived.
  - Scheduled `pg_basebackup` with retention, removal of WAL that is no longer needed, and an optional mirror to S3.
  - A restore keeps the current data and puts it back automatically if the recovery fails. Restores can follow each other, including back to a time before an earlier restore.
  - Archiving failures are notified and exported to Prometheus.
- **PostgreSQL replicas and failover** (Connection tab):
  - Streaming hot standbys on the same or another server, with a replication slot and their own read-only URL. Lag is monitored, and a replica that disconnects sends a notification.
  - **Promote** runs a failover: the primary is stopped first, then the replica becomes the database under the same name, so applications keep their connection URL.
  - Optional automatic failover when the primary's server stays unreachable. A former primary is stopped as soon as its server answers again.
- **Git over SSH** for GitLab, Bitbucket and Gitea on premises (`git@host:group/app.git`, `ssh://git@host:7999/…`):
  - Every application has its own deploy key (generated or imported, stored encrypted), and the key is on disk only during the clone.
  - The Git server's host key is checked on every clone. A host is trusted on first use with its fingerprint written to the log, or only from the list administrators approve (*Settings → Git sources → SSH host keys*). A changed host key stops the deployment.
- **Compliance report** (*Settings → Compliance*): the evidence auditors ask for, for a period and for every project or one.
  - Security settings, accounts and 2FA, API tokens and protected environments.
  - Deployments with their requester and approver, and security scans.
  - Backups with failures and test restores, point-in-time recovery, incidents, alerts and the audit log.
  - Printable HTML, or a ZIP with HTML, JSON, CSV and SHA-256 checksums; every export is audited.
- **AI assistant with local models**: besides OpenRouter, the assistant works with any OpenAI-compatible server in your network (Ollama, vLLM, LiteLLM, LocalAI, llama.cpp), so it also works offline and no message leaves the network. The address is set in *Settings → AI assistant*, the key is optional, and the model list comes from the server.
- **Shared variables**: set once for the organization (*Settings → Shared variables*), a project or one environment (project page → **Variables**).
  - The narrowest scope wins, down to the application's own variables.
  - Applications show the variables they inherit.
  - **Compare with another environment** shows how staging and production differ, with the source of each value, and copies the selected variables over.
- **Import from Coolify, Heroku and Dokku** (*Settings → Import*): PortDock reads the other platform, shows the plan, and creates the items you tick, stopped or deployed.
  - Coolify, through its API: projects and environments, applications (Git or image, build pack, port, domains, health check, limits, commands, variables, storage, scheduled tasks), databases and one-click services.
  - Heroku, with an API key: applications with config vars, custom domains and dynos, building from Heroku Git; Postgres, MySQL and Redis add-ons.
  - Dokku, over SSH: applications from the images Dokku built, with variables, domains, port, scale and storage; datastore plugins.
  - Databases and volumes are created empty; every item lists what did not carry over. Tested against a real Dokku 0.38.
  - An image that is in no registry (built on the server, loaded by hand) now deploys from the server instead of failing to pull.
- **Service catalogs and an open template format**: one-click services are now plain compose files with an `x-portdock` block, so anyone can write one.
  - 31 built-in services (18 new: Keycloak, Nextcloud, Jenkins, Open WebUI with Ollama, Directus, Wiki.js, BookStack, Matomo, Mailpit, ntfy, Gotify, Stirling-PDF, IT-Tools, Excalidraw, Adminer, Redis Insight, code-server, listmonk).
  - *Settings → Service catalogs* adds catalogs from a URL (refreshed daily) or a file: the PortDock community catalog from this repository, your own, or **Coolify's 350+ templates**, converted on the fly.
  - The picker searches every catalog by name, category, tag or source, shows logos, and tells which templates need host access or variables first; templates from a catalog deploy without host access unless an administrator allows it, and never with the Docker socket.
  - `pdctl template lint`, `pdctl template bundle` and `pdctl template convert` (Coolify) help write and publish templates.
- **Secret managers: HashiCorp Vault and Azure Key Vault** (*Settings → Secret managers*): a variable can read its value from a vault instead of storing it.
  - Vault (or OpenBao) with a token or AppRole, KV v2 or v1, namespaces; Key Vault with an app registration or the managed identity of an Azure VM, secret versions and JSON secrets read key by key. An internal CA certificate and the corporate proxy are supported.
  - The value is read when a deployment, job or service starts, masked in logs and never stored. A secret that cannot be read stops the deployment before anything changes, with the reason in its log.
  - A store can be limited to some projects and to a path prefix; credentials are encrypted and never shown again. *Test connection* and the variable editor's *Check* list the keys of a path, never the values.
  - In `portdock.yaml` under `secret_refs` (`DB_PASSWORD: vault-prod:shop/db#password`), with `pdctl env set APP KEY --from …`, with `secret_ref` on the Terraform `portdock_env_var`, and in the compliance report.
- **Canary deployments** (Configuration → Deployment strategy):
  - The new version first gets 5–50 % of the traffic through a Traefik weighted service, while PortDock watches its share of server errors and its containers.
  - It is rolled back automatically when it does worse than allowed (and clearly worse than the current version), and promoted after the observation time.
  - The deployment page shows the live numbers with **Promote now** and **Roll back**.
  - The proxy now exposes its request metrics inside its container for this, so existing proxies are recreated once after the update.
- The `deployment.success` notification now includes the duration, the commit message and the application's address.
- **Observability** (*Settings → Observability*), to plug PortDock into the monitoring stack you already run:
  - **Prometheus metrics** at `GET /api/metrics`, scraped with an API token. They cover:
    - servers, plus applications, databases and services labelled with project, environment and name;
    - deployments, scheduled jobs and database backups;
    - TLS certificate expiry, uptime monitors and firing alerts.
  - **Log drains** to Grafana Loki, Elasticsearch / OpenSearch, Graylog (GELF), Splunk HEC, syslog (RFC 5424, also over TLS) or any HTTP endpoint:
    - A Vector agent on each server ships the logs of every container, labelled with project, environment, application, server and deployment.
    - Each destination gets a 256 MB disk buffer.
    - A destination can be limited to some projects.
    - The settings page shows delivery counters and errors, and *Send a test line* checks every destination end to end.
  - **OpenTelemetry**: set an OTLP endpoint and applications instrumented with an OpenTelemetry SDK send their traces, metrics and logs to it. Each deployment sets `OTEL_EXPORTER_OTLP_*`, `OTEL_SERVICE_NAME` and the resource attributes (project, environment, commit). Applications that configure OpenTelemetry themselves are left alone.
- **MCP server for AI agents**: PortDock speaks the [Model Context Protocol](https://modelcontextprotocol.io) at `POST /api/mcp` (Streamable HTTP), so Claude Code, VS Code, Cursor and other agents can work with your applications.
  - Tools to list projects, applications, databases, servers and alerts, deploy (and wait for the result), read a deployment's status and log, read application logs, roll back, restart and back up a database.
  - It takes an API token, and the token's scope and projects apply to each tool: a `read` token can only look, a `deploy` token can also deploy and roll back. Protected environments still need an approval, and every action is in the audit log.
  - `pdctl mcp` serves the same tools on standard input and output for clients that start a local command (Claude Desktop, Cursor, Windsurf).
  - *Settings → API tokens → AI agents* shows the configuration for each client.
- **Configuration as code:**
  - **`portdock.yaml`** declares the applications of a project and environment: source, build, port, replicas, limits, health check, domains, variables, persistent storage, jobs and access protection. `pdctl apply -f portdock.yaml` creates what is missing and changes only what differs (`--dry-run` shows the plan, `prune: true` removes what the file no longer lists). Secret values stay in PortDock; the file lists only their names.
  - **`pdctl`**, the command-line client, in the image and attached to the release for Linux, macOS and Windows: `deploy --wait`, `env list|set|unset`, `jobs`, `run`, `apply`, `export` (writes the `portdock.yaml` of an existing application).
  - A **Terraform provider** (`portdock_project`, `portdock_environment`, `portdock_application`, `portdock_domain`, `portdock_env_var`, data source `portdock_server`), attached to the release for a filesystem mirror. See [terraform-provider-portdock](https://github.com/gavrilencu/PortDock/tree/main/terraform-provider-portdock).
  - **OpenAPI 3.1**: `GET /api/openapi.json` describes every endpoint with the token scope it needs; *Settings → API tokens → API reference* shows it in the browser.

### Fixes

- The API example in *Settings → API tokens* showed an old token prefix (`sy_`) instead of `pd_`.
- The notification channels can now subscribe to `backup.restore_failed` and `database.failed`, which were sent but could not be selected.

- Uploading database backups to S3 works again: since v1.12 the access key is stored encrypted and was sent as is. The S3 credentials are now passed to `aws-cli` through a temporary file instead of the command line.
- The S3 settings show that an access key is stored instead of an empty field.
- A data race in the Containers page (servers queried in parallel) is fixed.
- Built with Go 1.27.2, which fixes 12 vulnerabilities of the Go 1.27.0 standard library (net/http, crypto/tls, html/template).
