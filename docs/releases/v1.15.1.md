## The AI assistant reads your platform, proposes actions you confirm, and knows the documentation

Until now the assistant could only answer from what you pasted into the chat. It now sees the instance with your own permissions, investigates problems itself, and can propose a few actions that run only after you confirm them.

### New

- **The assistant sees your instance.** Ask *Which containers have problems right now?*, *Show me the errors in the logs of my containers* or *Why did the last deployment fail?*: the assistant finds the container, application or deployment you mean, reads the evidence and explains the probable cause and the fix in PortDock terms, naming the tab or setting. Its tools read:
  - projects, applications with their settings, domains (DNS and certificate status), scheduled jobs and saved versions;
  - deployments with the end of their build and rollout log, and the logs of a running application;
  - the containers of every server, with their logs (only the error lines, a text filter and the most repeated lines), inspect data (exit code, OOM, restarts, health check) and live CPU, memory and network usage;
  - databases with their backups (never their password or connection URL), services, servers and their health, metrics history;
  - alerts, uptime monitors and the recent activity of the audit log.
- **With your permissions, and nothing more.** Every tool goes through the API with the user's own session, so project roles, visibility and token limits apply exactly as in the interface: nobody sees through the assistant what they cannot open themselves. Values that look like credentials in logs (passwords, tokens, API keys, connection strings) are masked before anything reaches the model.
- **You see what it did.** The chat shows each step of a reply as it happens (*Reading the logs of container …*, *Inspecting container …*, *Searching the documentation for …*) and keeps the steps with the reply in the history.
- **Actions you confirm.** The assistant can propose a deployment, a rollback to an earlier version, a restart or start of an application, container, database or service, a backup of a database now, or a run of a scheduled job. Proposing is not running: a card in the chat says what the action will do, it runs only when you press **Confirm**, with your own rights (a protected environment still needs its approval), and it is written to the audit log. A proposal not confirmed within 15 minutes expires.
- **It can never break anything.** There is no tool that deletes, removes, stops, kills or prunes anything, or that changes variables, domains, settings, users or tokens, and the API refuses such requests made for the assistant even if a model tried. Administrators can turn the actions off, or the tools altogether, in *Settings → AI assistant → Access to the platform*; both are on by default.
- **It knows the documentation.** PortDock's documentation and troubleshooting playbooks (deployments, container exit codes, Traefik 404 / 502, DNS and TLS, databases, servers, updates) are embedded in the binary and searched locally, so *how does PortDock…* questions are answered from the documentation with the menu path, offline too, instead of being guessed.
- **It knows where you are.** The page you are looking at (an application, a database, a server, the Containers page…) is given to the assistant, so *this application* or *this server* means something.
- Works with OpenRouter and with the local OpenAI-compatible servers (Ollama, vLLM, LiteLLM, llama.cpp) using the standard tool-calling API. A model that does not support tools answers without them, with a notice in the chat.

### Notes

- The tools need a model with tool calling (function calling). Most current models on OpenRouter have it; on a local server pick a model that advertises tools (for example `qwen2.5` or `llama3.1` with Ollama). Larger models investigate much better than tiny ones.
- Each reply is bounded: up to 8 rounds of tools and 16 tool calls, 2000 log lines per call and a limited size per tool result, so a chatty model cannot run away.
- Log timestamps given to the model are UTC. Container names look like `<application uuid>-<deployment id>`; databases and services use their uuid.
- For contributors: changes to `README.md` or to the service templates README must be copied into the assistant's embedded documentation with `make docs-sync` (`go test ./internal/assistant` fails otherwise).

### Fixes

- Built with Go 1.27.3, which fixes GO-2026-6809 in `crypto/x509` (compromised intermediate certificates are now distrusted when verifying TLS certificates, e.g. for LDAP over TLS).
- v1.15.0 was tagged but never published: its release workflow stopped at the vulnerability check above, so nothing was built or released. v1.15.1 is the same code built with Go 1.27.3.
