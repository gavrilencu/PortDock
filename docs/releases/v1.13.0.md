## Persistent storage for applications

Applications can now keep data across deployments without hand-written `docker run` options.

### New

- **Storage tab** on every application: add a volume with a name and the path inside the container where the application writes, e.g. `data` → `/app/data`. Files written there survive redeploys, restarts and rollbacks. Volumes can be mounted read-only.
- **Docker volumes managed by PortDock**, named `pd-<application uuid>_<name>` and created on each server of the application at the next deployment. Each server keeps its own copy; replicas on a server, and the old and new version during a rollout, share it. The tab shows on which servers each volume exists.
- **Server directories** (bind mounts) for administrators. The root, system directories, the Docker socket and PortDock's own data directory can never be mounted.
- **Pull request previews get their own empty volumes** and no server directories, so a preview cannot change production data; closing the preview deletes them.
- **Removing a volume keeps its data** by default; *Delete with data* removes the Docker volume on every server. A volume still used by a container is left in place with a clear message, and volumes that are no longer mounted are listed under *Leftover data* to be deleted later.
- **Deleting an application** with volumes offers *Delete, keep volumes* or *Delete with data*. Until now the volumes of an application were never removed.
- Application volumes appear in *Containers → Volumes* next to the application they belong to.

### Notes

- Changes to volumes apply on the next deployment.
- Docker Compose applications keep declaring their volumes in `docker-compose.yml`; the Storage tab is not shown for them.
- Volumes added earlier through *Custom docker run options* (`-v name:/path`) keep working; to manage one from the Storage tab, remove the option and add the volume there (use a new name, or move the data, since managed volumes are named `pd-<uuid>_<name>`).
