## PortDock on Kubernetes in one command: a fresh server, your domain, test and prod ready

On a fresh Linux server, one command now installs everything PortDock needs to deploy to Kubernetes, and asks you only for the domain of the dashboard:

```bash
curl -fsSL https://github.com/gavrilencu/PortDock/releases/download/v1.17.0/install-kubernetes.sh | sudo bash
```

When it ends, it prints a link. Open it, create your account, connect GitHub, and deploy.

### New

- **An all-in-one installer** (`install-kubernetes.sh`, attached to the release). It installs and connects:
  - **k3s**, with Traefik on ports 80 and 443, local storage and metrics-server;
  - **cert-manager** with a Let's Encrypt `ClusterIssuer`: the dashboard and every application domain get an HTTPS certificate on their own, and HTTP redirects to HTTPS;
  - **Docker**, where the images of applications from Git are built;
  - a **private container registry** on the same domain (`https://<domain>/v2/`), with a generated password;
  - **PortDock** on `https://<your domain>`.

  It checks that the domain points to the server before it starts. Running it again updates PortDock (`PORTDOCK_VERSION=vX.Y.Z` for a given version) or repairs the setup, keeping the passwords and the data. Without a terminal: `PORTDOCK_DOMAIN=panel.example.com`.
- **Ready when you sign in.** The owner account finds its servers set up:
  - **test** and **prod**, two namespaces of the cluster (`portdock-test`, `portdock-prod`), with certificates from Let's Encrypt;
  - **build**, the server's Docker, which builds the images. It has no proxy, because ports 80 and 443 belong to the cluster;
  - the registry, used by both clusters.
- **A setup token protects the first-run page.** The link the installer prints (`https://<domain>/login#setup=…`) carries the token, so nobody who finds the fresh dashboard on the internet can create the owner account before you. Without the link, the page asks for the token, and `kubectl -n portdock get secret portdock-setup -o jsonpath='{.data.token}' | base64 -d` shows it. Restoring a backup on the first-run page needs the token too.
- **A registry for the cluster** (*Servers → a cluster → Settings → Registry of the cluster*). Applications built from Git that have no registry of their own push their images there, and the cluster pulls them. Until now, each application had to choose a registry, or its deployment stopped with *an application built from Git needs a container registry on Kubernetes*. The application's settings show the registry it will use.
- **New resources go to the right server.** On an instance whose only Docker server just builds, a new application goes to a cluster: the one named like the project's environment (`production` → prod, `test` → test). Databases, services and Compose stacks still go to a Docker server.

### Notes

- Point the domain's DNS record (A) to the server before running the installer. The certificate is issued as soon as Let's Encrypt reaches the server on port 80.
- PortDock's data is in `/data/portdock` on the server, and the registry's images in a volume of the cluster.
- What needs Docker (databases, one-click services, Compose applications) still runs on a Docker server, not in the clusters. The **build** server has no proxy, so its applications get no domains: use test or prod for applications.
- New settings for PortDock in a pod, used by the installer: `PORTDOCK_SETUP_TOKEN`, `PORTDOCK_KUBE_SERVERS` (`name=namespace` pairs), `PORTDOCK_KUBE_CLUSTER_ISSUER` and `PORTDOCK_REGISTRY_HOST` / `_USERNAME` / `_PASSWORD`. Without them, nothing changes.
- The database gains a column for the registry of a cluster; existing servers have none.
