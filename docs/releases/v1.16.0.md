## Kubernetes clusters as servers

A Kubernetes cluster can now be a server, next to Docker servers. PortDock works in one namespace of it, with `kubectl` and the credentials you give it, and installs nothing on the cluster. Docker servers work exactly as before.

### Connect a cluster in one command

Where `kubectl` reaches the cluster:

```bash
curl -fsSL https://raw.githubusercontent.com/gavrilencu/PortDock/main/deploy/kubernetes/connect.sh | bash
```

It creates the namespace `portdock`, a service account that administers that namespace only, and prints a kubeconfig. Paste it in **Servers → Connect server → Kubernetes cluster**. **Check the cluster** on the server's page then reports the namespace and its permissions, the ingress controller, cert-manager and the metrics API.

The kubeconfig is stored encrypted and never shown again. One that runs a program to sign in (`exec`, as the files of EKS, GKE and AKS do) or points to files is refused, because it would act on the machine PortDock runs on: use a service account token.

### What a deployment does on a cluster

- **Image.** A prebuilt image is pulled by the cluster. An application from Git is built as usual on a Docker server (its build server, or the one PortDock runs on) and pushed to its registry, where the cluster pulls it with a pull secret PortDock creates.
- **No downtime.** The application is a Deployment with a rolling update: new pods must answer the health check before old ones stop. A version that does not start is rolled back; one that cannot start at all (an image that cannot be pulled, a crash loop) fails within seconds, with the pod's events and logs in the deployment log.
- **Variables** are a Secret of that deployment, so a version that is rolled back keeps the variables it started with.
- **Domains** are an Ingress (port and path prefix per domain), with a certificate per HTTPS domain from a cert-manager `ClusterIssuer`. Changes apply without a deployment.
- **Versions and rollbacks** work as on Docker; a prebuilt image is pinned to the digest the cluster pulled.
- **Persistent storage** is a PersistentVolumeClaim per volume, kept across deployments.
- **Pre-deploy commands and scheduled jobs** run as a Job in a pod like the application's; the post-deploy command runs in a pod of the new version.
- Replicas, CPU and memory limits, logs, the terminal in a pod, start / stop / restart, the containers page, the topology map, the metrics history and the Prometheus endpoint work as on Docker servers.

### PortDock inside the cluster

```bash
kubectl apply -f https://raw.githubusercontent.com/gavrilencu/PortDock/main/deploy/kubernetes/portdock.yaml
kubectl -n portdock port-forward svc/portdock 8000:8000   # then open http://localhost:8000
```

PortDock runs as a StatefulSet with its data on a volume. The cluster is there as a server from the start, reached with the pod's service account, and applications go to the namespace `portdock-apps`.

### Not on Kubernetes yet

Use a Docker server for these: databases, one-click services and Docker Compose applications; pull request previews; canary deployments; www redirects and uploaded certificates; log drains and dynamic scans (DAST); host port mappings, custom Docker options and server directories as volumes. Images are built on a Docker server, not in the cluster, so a PortDock that runs inside a cluster needs a Docker server as the build server of applications from Git.

**Access protection** (single sign-on, password, allowed addresses, rate limit) is not enforced on Kubernetes yet. An application that has it is not published at all there, rather than published without it.
